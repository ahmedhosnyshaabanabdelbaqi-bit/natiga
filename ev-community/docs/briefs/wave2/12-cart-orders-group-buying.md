## Rules (see BUSINESS_RULES §6–7 — binding)
- `CartService::forUser($user)` (server-side; guest carts by session merged at login), `count($user)` shared as Inertia prop `cartCount` (Inertia::share in CartServiceProvider; the public layout already reads `cartCount`). Add/update/remove with quantity limits (`max_per_order`), stock awareness (available from `InventoryService::availableFor` when the Inventory module exists; else availability flag), fulfillment groups displayed clearly.
- Checkout (`PlaceOrder` action, transactional, idempotent via `Idempotency::run('orders.place', cartHash + user)`): revalidate every line (current price via `ProductVariant::currentPrice()`, active status, availability, compatibility via `CompatibilityEngine` for the selected vehicle — `not_compatible` blocks, `needs_verification` requires explicit acknowledgement and yields order status `awaiting_compatibility`), compute totals with `Money`, deposit per fulfillment type/group buy (`orders.deposit_percentage` default 30, group buy deposit rule), expected arrival (group buy / china order lead time setting), cancellation policy + terms version (from policy_versions), snapshot everything, reserve stock for in-stock items (`InventoryService::reserve`) — reservation failure → domain error, cart untouched; write `order_charge` ledger entry through `App\Modules\Accounting\Services\LedgerService::charge($order)` if it exists (class_exists guard; otherwise dispatch `OrderConfirmed` event so Accounting attaches later — document this hand-off clearly); order number ORD-YYYY-NNNNNN; clear the cart; notify member (orders.placed).
- Status machine in `OrderStatus` enum with `canTransitionTo()`; transitions only through `OrderService::transition($order, $to, $actor, $reason)` writing history + audit; payment_status/shipping_status/delivery_status recomputed by public methods called from Payments/Shipping/Deliveries modules (`OrderService::recalculatePayment($order)`, `recalculateShipping`, `recalculateDelivery`) using the contract quantity columns on order_items; `completed` only when all items delivered (or cancelled remainder) and paid.
- Staff edits: quantity/price override with reason + audit + adjustment row; a total increase requires member approval (notification + member approve/decline page) before it applies. Cancellation by member allowed while `awaiting_payment`/`awaiting_compatibility` (and `confirmed` before procurement per setting) — releases reservations, writes reversal via LedgerService if present, records cancellation; refunds handled by Accounting.
- Group buys: admin creates (draft → open); members register interest (no commitment) or join (creates an order with the group-buy fulfillment type and deposit); progress = confirmed quantity vs minimum, shown publicly without identities; deadline job (`group-buys:process-deadlines`, scheduled hourly): min reached → `confirmed` (notify participants); not reached → admin decision page (extend with reason → audit, or cancel → orders cancelled, deposits become refund requests via Accounting if present); price change after confirmations → `group_buy_member_approvals` rows, notify, each member approves/declines (decline cancels their order); `ordered` when a PO is linked (Procurement sets `purchase_orders.group_buy_id`); `completed` when all orders delivered. Smart opportunities report (admin): candidates from wishlist interest + search demand (from Catalog `search_logs` if provided) + part requests + previous orders, ranked; "create group buy" prefilled — never automatic.
