## Rules (BUSINESS_RULES §1–5 are binding — read them again)
- `LedgerService`: `charge(Order)` (idempotent per order), `credit(Payment)`, `refundDebit(Refund)`, `adjust(FinancialAdjustment)`, `reverse(LedgerEntry, reason, actor)`, `balance(User)`, `outstanding(User)`, `orderOutstanding(Order)`, `unallocatedFunds(User)`, `statement(User, from, to)`; entries are append-only (model guard against update/delete) and dated in an open period (`FinancialPeriods::assertOpen($date)` → DomainException `core.errors.financial_period_closed`).
- `SubmitPayment` (member or staff): amount > 0, method, reference, received_at, proof attachment(s) via AttachmentService (private; viewable by owner + payments.view); status pending_review; NO ledger effect (test §267). `ApprovePayment` (payments.approve, actor must have MFA — enforced by admin.portal already): transaction + row lock + idempotency (repeat → same result, no duplicate ledger/receipt — test §268) → status approved → `LedgerService::credit` → allocations (explicit list validated Σ ≤ amount, or auto oldest-outstanding-first; each allocation ≤ order outstanding) → receipt row (NumberSequence 'receipt') → `GenerateReceiptPdf` queued job (PdfService receipt view AR/EN by member locale, stored as private attachment, receipt_versions) → audit `payments.approved` → after commit Notify member (payments.approved, dedup) → `OrderService::recalculatePayment` for touched orders (class_exists guard). `RejectPayment` (reason) and `ReversePayment` (payments.adjust + reason + open period; reversal entries, deallocate, void receipt + regenerate void PDF, audit + security event `large_refund_approved` analog `payment_reversed`).
- Member financial account (`/account/payments`): confirmed order value, approved payments, outstanding, upcoming installments (deposit vs remaining per order with due dates from settings), refunds, credit balance, unallocated funds; statement PDF download (`statement` view).
- Refunds: `RequestRefund` (member for cancelled orders/unallocated funds, or staff), refundable amount rule, `ApproveRefund` (refunds.approve; second approver when amount ≥ `accounting.refund_dual_approval_threshold` (setting, default 5,000) — same user cannot approve twice; security event on large approval), `RecordRefundPayout` (method/reference/date → status paid → `refundDebit`), `FailRefund`, `RejectRefund` (reason); refunds in closed periods dated in the open period.
- Adjustments: reason required; dual approval above `accounting.adjustment_dual_approval_threshold`; posting writes ledger entry; audit.
- Financial periods: monthly rows auto-created by scheduler; `close(period, actor)` requires accounting.close_period, reconciliation pass (see below), no pending_review payments dated inside (or explicit `waiver_note`) → closed; reopening only by owner with reason.
- `finance:reconcile [--period=] [--member=]` command: checks invariants (BUSINESS_RULES §16): Σ charges − reversals = Σ confirmed order totals; Σ allocations ≤ payment amount & ≤ order total; refunds paid ≤ approved allocations; every approved payment has exactly one credit entry and one receipt; receipt numbers unique; balance recomputation equals cached read models (if any); output Passed/Warnings/Failures + exception rows (member, transaction, expected, actual, difference) → OperationsExceptions (finance, P1) — never auto-fixes. Register HealthChecks (unallocated approved payments > N days, payments pending_verification, duplicate references).
- Bank reconciliation: upload CSV/XLSX statement via the Imports framework parser (or openspout directly), dedupe statement by hash, suggest matches by amount + date ±3 days + reference/member number/order number similarity → confidence score; accountant confirms match (creates/approves? No: confirms match only; approval stays a separate explicit action but the UI offers "approve payment" with the match) or ignores; unmatched rows listed; duplicate rows flagged.
- Gateway (optional): `PaymentGatewayService::createTransaction(Order, amount)` via `Integrations::payment()` (NotConfigured → button disabled with explanation), redirect result never trusted; `WebhookHandlers::register('payment', ...)` verifies amount/currency/order/provider ref/signature, idempotent by provider ref (test §269), timeout → `pending_verification` + `payments:reconcile-pending` scheduled command calling `verifyTransaction`.
