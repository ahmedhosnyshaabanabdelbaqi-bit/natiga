## Rules
- Partner scoping: `User::currentCenter()` (resolveRelationUsing / macro) returns the active `center_users` row's center; the partner portal middleware already checks `partner.access`; every partner query uses `->forCenter($center)`; policies: a center user sees only their center (and, for employees, only their branch when `branch_id` set). Center A can never see center B's branches/users/quotes/bookings — IDOR tests.
- Center admin manages branches, services & prices, resources & availability, employees (invite by email → creates user with role service-center-employee + center_users row; cannot grant admin-panel roles).
- Admin approves centers (`centers.approve`), sets platform fee & payment mode; approval audited; supported vehicles pivot maintained by the center.
- Availability engine (public service used by the Maintenance module): `AvailabilityService::slots(CenterBranch, Service, Carbon $day): array<{starts_at, ends_at, resources}>` computing free slots from working hours, resource availability, blackouts and existing holds/bookings (`maintenance_bookings` table read only if it exists) — the Maintenance engineer will call `AvailabilityService::hold(...)`/`release(...)`; define these methods now with a `resource_holds` table (resource_id, starts_at, ends_at, reference_type/id, expires_at) and a row-locked implementation.

Registrations: partner dashboard KPIs (`branches_active`, `services_active`), audience `service_center_customers` (uses bookings table if present), importer for centers.
