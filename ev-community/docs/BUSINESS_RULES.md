# Business rules (authoritative)

These rules are implemented in module actions/services and covered by tests. Any change goes through the change-management process (`DEPLOYMENT.md`).

## 1. Money
- All amounts are decimals with 2 fraction digits (EGP), stored as `decimal(14,2)`; arithmetic uses `App\Support\Money\Money` (brick/money, HALF_UP). Floats are never used for money.
- Base currency EGP. Foreign-currency costs (USD/CNY/EUR…) store `original_amount`, `original_currency`, `fx_rate`, `fx_source`, `fx_rate_date` and the converted EGP amount. Historical transactions are never revalued when rates change.
- Allocation of an amount across items (cost allocation, discounts, payment allocations) must sum exactly to the original amount; rounding remainders go to the largest fractional parts (`Money::allocate`). Any documented rounding difference is recorded as an explicit accounting entry.

## 2. Member balance (ledger)
- `member_ledger_entries` is append-only. Entry types: `order_charge` (debit), `payment_credit` (credit), `refund_debit` (debit), `adjustment_debit`, `adjustment_credit`, `reversal` (opposite sign of the reversed entry, references it).
- **Balance = Σ credits − Σ debits** computed from the ledger (`LedgerService::balance`). `Outstanding` for a member = Σ open order charges − Σ approved payment allocations to those orders (never negative per order). `Credit balance` = approved payments not allocated to any order (unallocated funds) + credit adjustments.
- Every order confirmation writes exactly one `order_charge` entry (idempotent on order). Cancelling an order writes a `reversal` of the charge (and releases allocations to unallocated funds).
- Corrections after posting are done only by reversal + new entry, never by editing. Manual adjustments require a reason and `payments.adjust`; above `accounting.adjustment_dual_approval_threshold` they require a second approver (maker/checker).

## 3. Payments
- Methods: bank transfer, approved collection account, cash by authorized staff, (gateway when configured).
- A member submits a payment with amount, method, reference, date and proof attachment. Status `pending_review`. **Submission never changes the balance or the order.**
- Approval (`payments.approve`, MFA-protected role) runs in one transaction: lock payment row → if already approved return (idempotent) → set approved → write `payment_credit` ledger entry → allocate to orders (explicit allocations chosen by the approver, or automatic oldest-outstanding-first if none given; Σ allocations ≤ payment amount, remainder stays unallocated) → create receipt row with `RCT-YYYY-NNNNNN` (unique; PDF generated by a queued job) → audit entry. Duplicate approval requests (same idempotency key or repeated click) produce one approval, one ledger entry, one receipt.
- Rejection requires a reason; reversal of an approved payment requires `payments.adjust`, a reason, an open financial period, and writes a `reversal` entry plus deallocation; the receipt is marked void (never deleted), and a void receipt PDF is regenerated.
- Gateway payments: the server creates the transaction and verifies the result (amount, currency, order, transaction id, signature) via the provider; redirect success pages are never trusted; webhooks are idempotent by external event id; timeouts leave the payment in `pending_verification` for scheduled reconciliation.
- Approved payments can be allocated to several orders; an order's `paid_amount` and `outstanding_amount` are read models recomputed from allocations after every change and validated by `finance:reconcile`.

## 4. Refunds
- `requested` (member or staff) → `approved` (single approver below `accounting.refund_dual_approval_threshold`, two distinct approvers above) → `processing` → `paid` only when the actual payout is recorded (reference, date, method) → or `failed`/`rejected`/`cancelled`.
- Refundable amount ≤ approved allocations for the order minus previous refunds; a refund writes `refund_debit` at approval? **No:** the ledger effect (`refund_debit`) is written when the refund is **paid**; approval only reserves it (shown as "pending refund"). Refunds after a closed period are allowed only as new entries in the open period.

## 5. Financial periods
- Periods (month) are `open` → `closing` → `closed`. Closing requires `accounting.close_period`, a passing reconciliation run, and no payments in `pending_review` dated inside the period (or an explicit waiver noted). After closing, entries dated inside the period cannot be created/edited; corrections are dated in the open period and reference the original.
- Group buys and shipments can be "financially closed" the same way (no further cost allocation changes).

## 6. Orders & checkout
- Cart is server-side. Checkout re-validates price (current variant price), availability, quantity limits and compatibility for the selected vehicle; a `not_compatible` item cannot be ordered as compatible (the member must remove it or explicitly acknowledge "order anyway, not verified" which sets the item compatibility to `needs_verification` and the order to `awaiting_compatibility` for staff review).
- Order snapshot (items, prices, terms, deposit rule, cancellation policy version, delivery method) is frozen at confirmation; later product/price changes never affect it. A price change on a confirmed order is a staff action (`orders.edit`, reason, audit, member approval when the total increases).
- Statuses: `draft` → `awaiting_compatibility` → `awaiting_payment` → `confirmed` (deposit or full payment approved as configured per fulfillment type) → `processing` → `ready` → `partially_delivered` → `completed`; `cancelled` from any state before delivery starts (refund rules apply). Payment/shipping/delivery statuses are tracked separately and derived from allocations/shipments/deliveries.
- Deposit rule: percentage or fixed per group buy / fulfillment type (`orders.deposit_percentage` default 30%); `confirmed` requires approved payments ≥ deposit.

## 7. Group buying
- Interest ≠ commitment. `interested` members are counted for demand only. `confirmed` participation requires an order (and deposit when the group buy demands it).
- Progress shows confirmed quantity vs minimum without revealing member identities. Reaching the minimum enables `confirmed`; not reaching it by the deadline allows `cancelled` (all deposits become refunds or unallocated credit per member choice) or an extension (audited).
- A price change after confirmations requires member re-approval (each participant accepts/declines; declines are cancelled with refund rights).

## 8. Procurement, landed cost & allocation
- Purchase orders snapshot the FX rate. Landed cost = product cost + international shipping + insurance + customs + clearance + local transport + other + management fee, kept as *estimated* (planning) and *final* (actual invoices).
- Allocation of shipment expenses to items uses the rule stored with the allocation (weight/volume/value/quantity/manual approved); the allocated amounts sum exactly to the expense.

## 9. Shipments
- Many orders → one shipment and one order → many shipments are both supported through `shipment_allocations` (shipment item ↔ order item quantity).
- Status transitions are recorded as events with `source` = `manual` (staff) or `integration` (carrier API). No "live tracking" claim without an integration.
- Receiving records expected/received/short/damaged/rejected quantities per item; the identity `expected = received + short` and `received = accepted + damaged + rejected` must hold.

## 10. Inventory
- `inventory_movements` is the ledger; `inventory_items` quantities are read models reconciled from it. Types: receive(+), reserve (moves physical→reserved), release, transfer, deliver(−physical −reserved), return(+), damage (physical→damaged), adjustment(±, reason + `inventory.adjust`).
- **Available = physical − reserved − damaged − quarantine.** Reservation and delivery lock the item row (`FOR UPDATE`) and fail with a clear error if available < quantity; stock can never go negative (DB CHECK constraints).
- Reservations belong to an order item; releasing happens on cancellation or expiry; delivery consumes the reservation.

## 11. Events, slots & deliveries
- Slot capacity is enforced with a row lock and a `booked_count < capacity` atomic update; overbooked requests go to the waiting list; expiring reservations free the slot.
- Delivery: scan member/pickup QR → show ready items and payment eligibility (outstanding ≤ allowed threshold or fully paid, per setting) → confirm delivered quantities per item (≤ ready quantity, ≤ ordered − delivered) → one `delivery` record per handover, movements written, order item `delivered_quantity` updated, order status `partially_delivered`/`completed` derived. Idempotency key per scan + row locks guarantee a second device sees the new state instead of delivering again.
- Authorized pickup: the member registers a person (name, ID last digits, validity, order/event); the record is verified at pickup and logged.

## 12. Maintenance
- Quotes are compared per identical service scope only; a booking snapshots the quoted price. Center price changes never alter existing bookings.
- Capacity: bookings reserve the required resources (bay/technician/device) for the slot inside a transaction; the same resource cannot be double-booked; waiting list + expiring holds apply.
- Additional work is not approved until the member approves it (decision, timestamp, approved amount stored). Completion creates a verified `service_record` (platform verified) distinct from member-added records.
- Payment mode per service: pay center directly (platform records nothing financial) or pay platform (member payment → platform fee → center payable → settlement). Settlement = Σ eligible completed services + approved adjustments − platform fees − refunds − approved deductions; `paid` only when the payout is recorded.

## 13. Reviews & community content
- Reviews require a verified completed booking or verified purchase; moderated before publishing. Community charging reports and vehicle issue reports are shown as community experience, never as official status or diagnosis.

## 14. Charging data
- A station is published only with name, coordinates, source and last verification; stale data (older than `charging.freshness_days`) is flagged "needs verification". "Available now" is displayed only from a live integration with a fresh timestamp; otherwise "last known status + time" or "unknown". Price "free" is never assumed when unknown.

## 15. Recalls
- A recall is shown only with source, reference and verification date. Member vehicles are matched by make/model/year rules as "may apply to your vehicle"; VIN-level confirmation requires a real lookup source.

## 16. Reconciliation invariants (checked by commands, reported to the Exception Center, never auto-corrected)
- Σ order charges − Σ reversals = Σ confirmed order totals (per member and globally).
- Σ allocations of a payment ≤ payment amount; Σ allocations to an order ≤ order total.
- Σ refunds paid for an order ≤ Σ approved allocations to that order.
- Inventory: opening + receipts + returns + positive adjustments − deliveries − damage − negative adjustments = physical (per item).
- Orders: ordered = cancelled + allocated-not-shipped + shipped-not-received + received-not-ready + ready-not-delivered + delivered + returned (by status stage).
- Receipts unique per approved payment; no approved payment without a ledger credit; no delivery without movements.
