# نظام إدارة المحلات الصغيرة — نقطة البيع في القلب

نظام تشغيل متكامل للمحلات الصغيرة، **نقطة البيع هي قلبه وأعلى أولوية فيه**:
قاعدة بيانات فعلية، صلاحيات تُطبَّق على الخادم، عمليات مترابطة في معاملة واحدة،
واختبارات آلية تعمل على PostgreSQL حقيقي.

> **ليس نموذجًا تجريبيًا.** لا بيانات وهمية، ولا أزرار لا تعمل،
> ولا ادعاء بتكامل لم يُنفَّذ. ما لم يُنفَّذ مذكور صراحة في [`docs/STATUS.md`](docs/STATUS.md).

---

## في سطر واحد

نقطة بيع يستطيع الكاشير الاعتماد عليها أثناء الزحام، ويستطيع المالك تتبع
**كل فاتورة وحركة مخزون ومبلغ** من خلالها.

## البدء السريع

```bash
composer install && npm ci

cp .env.example .env && php artisan key:generate

sudo -u postgres psql -c "CREATE ROLE pos LOGIN PASSWORD 'change_me';"
sudo -u postgres psql -c "CREATE DATABASE pos_dev OWNER pos;"
# عدّل DB_* في .env ثم:

php artisan migrate --seed
npm run build

php artisan serve
```

افتح `http://localhost:8000` → يبدأ **معالج إعداد المحل**.

**حساب البداية:** `owner` / `ChangeMe!2026` — **غيّره فورًا**.

بيانات تجريبية (اختيارية، لا تُشغَّل تلقائيًا):
```bash
php artisan db:seed --class=DemoDataSeeder
```

التفاصيل الكاملة: [`docs/INSTALL.md`](docs/INSTALL.md)

## ما الذي يجعله جديرًا بالثقة

### المال لا يُحسب بأرقام عائمة — أبدًا
`numeric(18,4)` في قاعدة البيانات، `brick/math` في PHP بدقة عمل 6 خانات،
وحساب BigInt على نصوص في المتصفح. التقريب مرة واحدة فقط عند الحفظ أو العرض.

```
MoneyTest: جمع 0.01 ألف مرة  →  10.00 بالضبط
```

### البيع معاملة واحدة لا تتجزأ
الفاتورة + البنود + المدفوعات + حركات المخزون + حركات الخزنة + قيد العميل +
القيود المحاسبية — كلها أو لا شيء.
**لا فاتورة بلا مخزون، ولا حركة مالية بلا مستند.**

### التزامن مُختبَر بعمليات متوازية حقيقية
ثلاث عمليات نظام تشغيل منفصلة تحاول بيع **آخر قطعة** في اللحظة نفسها:
**فاتورة واحدة تنجح، واثنتان تُرفضان بسبب واضح**، والرصيد صفر بالضبط.

> هذا الاختبار كشف خطأ تسابق حقيقيًا في توليد أرقام المستندات أثناء التطوير، وأُصلح.

### منع التكرار على مستوى قاعدة البيانات
إرسال البيع مرتين ⇒ فاتورة واحدة والنتيجة نفسها تُعاد.
انقطع الرد؟ العميل **يستعلم بالمفتاح** بدل إنشاء فاتورة جديدة.

### الصلاحيات على الخادم لا في الواجهة
الكاشير لا يرى التكلفة ولا الربح **حتى لو طلبها من API مباشرة**.
موافقة المدير مرتبطة بالإجراء والمبلغ، أحادية الاستخدام، ويوقّعها المدير **بحسابه هو**.

### الخزنة تعرف الفرق بين المُسلَّم والمقبوض
فاتورة 70، العميل يسلّم 100 ⇒ الدرج: `+100` ثم `−30` باقٍ. الصافي 70، والتسليم موثّق.
فاتورة 1000 بـ400 نقدي و600 بطاقة ⇒ **الدرج يزيد 400 فقط**.

### المرتجع من الفاتورة الأصلية
سعرها وخصومها وضريبتها وتكلفتها الأصلية — لا سعر اليوم.
والتالف **لا يعود** لرصيد البيع.

### سجل التدقيق لا يُعدَّل
محفّز في قاعدة البيانات يرفض `UPDATE` و`DELETE` — وهذا **مُختبَر آليًا**.

### نسخة احتياطية مُثبَتة الاستعادة
تشفير AES-256، بصمة بجانب كل نسخة، و`--verify` يستعيد ويطابق **حقلًا بحقل**.

## الأداء — أرقام مقيسة فعليًا

على **10,000 صنف** و**50,000 فاتورة** (Xeon 2.8GHz، 4 أنوية، PostgreSQL افتراضي):

| العملية | p95 | الهدف | |
|---|---|---|---|
| مسح باركود وإضافة صنف | **9.0 مللي** | 150 مللي | ✅ أسرع 16× |
| اعتماد بيع كامل (3 بنود) | **89.7 مللي** | 2000 مللي | ✅ أسرع 22× |
| بحث نصي (50 نتيجة) | 108.6 مللي | — | مقبول |
| لوحة المالك (30 يومًا) | 36.1 مللي | — | جيد |

> أرقام قياس على هذه البيئة، وليست ضمانًا. زمن الأجهزة وخدمات الدفع خارج النطاق.
> التفاصيل ومواطن البطء: [`docs/TESTS.md`](docs/TESTS.md)

## الأنشطة المدعومة

بقالة وميني ماركت · ملابس وأحذية · موبايلات وإكسسوارات · مستحضرات تجميل وعطور ·
أدوات منزلية · مكتبات · كهرباء وسباكة · قطع غيار · تجزئة عامة.

**التخصيص من الإعدادات، بلا تعديل كود.** اختيار النشاط يفعّل ما يناسبه فقط،
والتغيير لاحقًا **لا يفقد البيانات**.

> ⚠️ **الصيدليات والأنشطة المنظمة غير مدعومة.** تحتاج وحدات ومتطلبات مستقلة،
> وإضافة منتجات لا تكفي.


## ما لا يدّعيه هذا النظام

- ❌ الامتثال لمنظومة الفواتير الإلكترونية — يحسب الضريبة فقط
- ❌ تكامل بنكي تلقائي — المدفوعات غير النقدية **تسجيل يدوي**
- ❌ الطباعة الصامتة وفتح الدرج آليًا — يحتاجان وسيطًا محليًا غير منفَّذ
- ❌ دعم كل طابعة وميزان — القائمة في [`docs/HARDWARE.md`](docs/HARDWARE.md)
- ❌ الصيدليات والأنشطة المنظمة
