# خريطة النظام وقواعد العمل الحرجة

> هذا المستند هو المرجع المعماري. يشرح **لماذا** صُمّم النظام بهذا الشكل،
> لا كيف يبدو فقط.

---

## 1. الترتيب الذي بُني عليه كل قرار

الأولويات كما طُلبت، ولها أثر مباشر في الكود:

| # | الأولوية | كيف ظهرت في التنفيذ |
|---|---|---|
| 1 | سلامة الأموال والبيانات | حساب عشري دقيق، معاملة قاعدة بيانات واحدة للبيع، أقفال صفوف، مفاتيح منع تكرار، قيود CHECK، سجل تدقيق غير قابل للتعديل |
| 2 | سرعة وسهولة نقطة البيع | بحث مفهرس، إضافة صنف بالباركود p95 = 9 مللي ثانية، إنهاء البيع النقدي بالكيبورد وحده |
| 3 | استقرار التشغيل | Outbox للطباعة والتكاملات، وضع محدود عند فقد الخادم، طابور مزامنة، نسخ احتياطي مُختبَر الاستعادة |
| 4 | التصميم | RTL افتراضي، سلة في اليمين، إجمالي وزر دفع ثابتان، بلا رسوم متحركة في مسار البيع |
| 5 | المزايا الإضافية | الولاء والعروض والحجوزات والتوصيل = وحدات اختيارية خلف Feature Flags، لا تظهر على شاشة الكاشير |

## 2. البنية العامة — Modular Monolith

```
pos/
├── app/
│   ├── Modules/                 ← منطق العمل، مفصول عن الواجهات
│   │   ├── Core/                الإعدادات، الفروع، المخازن، الكاشيرات، الترقيم، الاستيراد
│   │   ├── Access/              المستخدمون، الأدوار، الصلاحيات، الموافقات، سجل التدقيق
│   │   ├── Catalog/             المنتجات، المتغيرات، الوحدات، الباركود، الأسعار، السيريال، الدفعات
│   │   ├── Inventory/           سجل الحركات، الأرصدة، الحجوزات، التحويلات، الجرد
│   │   ├── Sales/               البيع، المرتجعات، الفواتير المعلقة، عروض الأسعار
│   │   ├── Purchasing/          أوامر الشراء، الاستلام، فواتير الموردين
│   │   ├── Customers/           العملاء، كشف الحساب، التحصيل
│   │   ├── Cash/                الورديات، الخزائن، حركات النقدية، المصروفات
│   │   ├── Accounting/          دليل الحسابات، القيود، الفترات
│   │   ├── Sync/                منع التكرار، العمليات المحلية، Outbox، مهام الطباعة
│   │   ├── Printing/            قوالب ومهام الطباعة
│   │   └── Reporting/           التقارير وتعريفاتها
│   ├── Support/                 Money, Quantity, DomainException  ← لا تعتمد على شيء
│   └── Http/                    Controllers, Middleware  ← طبقة رقيقة فوق الخدمات
├── resources/js/                Vue 3 + TypeScript + PWA
├── database/migrations/         مخطط قاعدة البيانات
└── tests/                       Unit / Feature / Concurrency
```

**القاعدة:** الوحدات تتخاطب عبر **الخدمات (Services)**، لا عبر النماذج مباشرة.
المتحكمات (Controllers) لا تحتوي منطق عمل — تتحقق من المدخلات، تستدعي خدمة، تُرجع النتيجة.

### اتجاه الاعتماد

```
Http ──> Services ──> Models ──> Database
             │
             └──> Support (Money/Quantity)   ← لا تعتمد على أي شيء
```

`SaleService` هو المنسّق الوحيد للبيع، ويستدعي:
`SaleTotalsCalculator` (حساب) · `PricingService` (سعر) · `InventoryService` (مخزون) ·
`SerialService` (سيريال) · `CashService` (خزنة) · `CustomerLedgerService` (مديونية) ·
`PostingService` (قيود) · `IdempotencyService` (منع تكرار) · `OutboxService` (آثار جانبية).

## 3. قواعد العمل الحرجة

### 3.1 المال ليس رقمًا عشريًا عائمًا — أبدًا

- كل المبالغ `numeric(18,4)` في PostgreSQL، وتعود من PDO **كنصوص**.
- الحساب داخل PHP عبر `App\Support\Money` فوق `brick/math` بدقة عمل **6 خانات**،
  والتقريب مرة واحدة فقط عند التخزين أو العرض.
- الواجهة تكرر نفس القواعد بحساب **BigInt على نصوص** (`resources/js/lib/money.ts`)
  لتعطي استجابة فورية، لكنها ترسل `expected_grand_total` والخادم **يرفض** أي اختلاف
  بدل أن يصححه بصمت.

> اختبار `MoneyTest::test_repeated_addition_does_not_drift` يجمع `0.01` ألف مرة
> ويتوقع `10.00` بالضبط.

### 3.2 ترتيب تطبيق قواعد المال — ثابت ومُختبَر

`config/pos.php → sales.calculation_order`

1. **خصم البند** (قيمة أو نسبة على `الكمية × السعر`)
2. **خصم الفاتورة** — يُوزَّع على البنود **بالتناسب** مع قيمتها بعد خصم البند
3. **الضريبة** — تُضاف (exclusive) أو تُستخرج من السعر المعروض (inclusive)
4. **تقريب النقدية** (اختياري) — يُسجَّل في `rounding_adjustment` منفصلًا فلا يختفي داخل الإيراد

**كسر التوزيع يذهب لأكبر بند**، فمجموع البنود يساوي الفاتورة بالضبط — لا يُخلق قرش ولا يضيع.
هذا ما يجعل المرتجع الجزئي دقيقًا: البند يحمل نصيبه الحقيقي من الخصم.

### 3.3 البيع = معاملة واحدة

`SaleService::performCheckout()` كلها داخل `DB::transaction`:
الفاتورة + البنود + المدفوعات + حركات المخزون + حركات الخزنة + قيد العميل + القيود المحاسبية.

إذا فشل جزء، لا يحدث شيء. **لا فاتورة بلا مخزون، ولا حركة مالية بلا مستند.**

الطباعة والتكاملات تُوضع في **Outbox** داخل المعاملة وتُنفَّذ بعد الـ commit.

### 3.4 التزامن — أقفال حقيقية لا افتراضات

| الخطر | الحماية |
|---|---|
| كاشيران يبيعان آخر قطعة | `SELECT ... FOR UPDATE` على صف `stock_balances (warehouse, variant)` |
| مرتجعان متزامنان لنفس البند | `UPDATE ... WHERE returned_qty_base + ? <= qty_base` (تحديث شرطي ذري) + قيد CHECK |
| ترقيم مستندين بنفس الرقم | `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` في عبارة واحدة |
| اعتماد فاتورة معلقة من جهازين | قفل تفاؤلي `version` يُفحص على الخادم |
| بيع نفس السيريال مرتين | `UNIQUE(serial_id)` على `sale_line_serials` + قفل الصف |
| ترحيل قيد مرتين لنفس المستند | `UNIQUE(source_type, source_id, purpose)` |

> اختبارات `tests/Concurrency/` تشغّل **عمليات نظام تشغيل متوازية حقيقية** على
> PostgreSQL حي، لا محاكاة داخل خيط واحد.

### 3.5 منع التكرار (Idempotency)

كل عملية مالية تحمل `Idempotency-Key`:

| الحالة | النتيجة |
|---|---|
| نفس المفتاح + نفس المحتوى، واكتملت | تُعاد **نفس النتيجة** (`replayed: true`) |
| نفس المفتاح + نفس المحتوى، وقيد التنفيذ | `409 idempotency_in_progress` |
| نفس المفتاح + محتوى **مختلف** | `409 idempotency_key_reused` |
| فشلت العملية | يُحرَّر المفتاح لتصح إعادة المحاولة |

المفتاح يُحجز بـ `INSERT ... ON CONFLICT DO NOTHING` (وليس بالتقاط استثناء)، لأن
عبارة فاشلة في PostgreSQL تُجهض المعاملة المحيطة كلها.

**عند انقطاع الرد:** العميل يستعلم `GET /sales/by-key/{key}` بدل إنشاء فاتورة جديدة.

### 3.6 المخزون — سجل مرجعي وأرصدة مشتقة

- `stock_movements` = **سجل غير قابل للتعديل**، كل تغيّر كمية له صف بمصدر وسبب ومستخدم ووقت.
- `stock_balances` = **إسقاط مشتق**، يمكن إعادة بنائه بالكامل (`rebuildBalance`)
  ومطابقته (`GET /inventory/reconcile`).
- الكميات دائمًا **بالوحدة الأساسية** داخل السجل، فالكرتونة والقطعة قابلتان للمقارنة.
- المخزون السالب ممنوع افتراضيًا؛ أي استثناء يحتاج سياسة معلنة.

**طريقة التكلفة: المتوسط المرجح المتحرك.**
- استلام: `المتوسط الجديد = (الكمية×المتوسط + الوارد×تكلفته) ÷ (الكمية + الوارد)`
- صرف: المتوسط لا يتغير، والحركة تُقيَّم بالمتوسط الجاري
- مرتجع: يعود **بتكلفته الأصلية** المسجلة في بند الفاتورة، لا بسعر الشراء اليوم

### 3.7 الخزنة — صفٌّ لكل جنيه

`النقد المتوقع = مجموع حركات الوردية الموقّعة`، وهي بالضبط المعادلة المطلوبة:

```
  عهدة البداية
+ مقبوضات المبيعات النقدية (sale_cash)
− الباقي المصروف للعملاء     (change_out)
+ التحصيلات والإيداعات        (collection / deposit)
− المرتجعات النقدية           (refund)
− المصروفات والسحوبات         (expense / withdrawal)
```

**لا ازدواج:** البيع النقدي يكتب `sale_cash`؛ تحصيل فاتورة آجلة يكتب `collection`.
مستندان مختلفان، صفّان مختلفان.

**فصل المُسلَّم عن الصافي:** عميل يدفع 100 على فاتورة 70 ⇒ `sale_cash +100` و`change_out −30`.
الدرج يزيد 70، والتسليم موثّق.

### 3.8 المرتجعات — من الفاتورة الأصلية

- القيمة من **بند الفاتورة الأصلي** (سعره ونصيبه من الخصمين وضريبته)، لا من سعر اليوم.
- التكلفة تُعكس **بتكلفة البيع الأصلية** المسجلة في البند.
- المصير إلزامي: صالح للبيع / تالف / فحص / مخزن مرتجعات — وغير الصالح **لا يعود** لرصيد البيع.
- في الآجل: تُخفَّض المديونية **أولًا**، وما زاد فقط يُرد نقدًا.
- المرتجع بدون فاتورة **مغلق افتراضيًا** (`features.return_without_invoice = false`).
- لا تُحذف فاتورة معتمدة ولا يُعدَّل تاريخها: مستندات عكس مترابطة فقط.

### 3.9 الصلاحيات على الخادم

- `EnsurePermission` middleware على كل مسار حساس؛ إخفاء الزر ليس حماية.
- **استجابات API تُفلتَر**: الكاشير لا يرى `cost_total` ولا `profit_total` حتى لو طلبها.
- موافقة المدير مرتبطة بـ (الإجراء + المبلغ + المستند)، تُستهلك مرة واحدة،
  ويوقّعها المدير **بحسابه هو** — لا يوجد كود مدير مشترك.
- لا يمكن لمدير اعتماد طلبه بنفسه.

### 3.10 العمل عند انقطاع الاتصال

يفرّق النظام بين ثلاث حالات:

| الحالة | المعنى | السلوك |
|---|---|---|
| `online` | الخادم يستجيب | كل شيء طبيعي (انقطاع الإنترنت لا يهم إن كان الخادم محليًا) |
| `degraded` | المتصفح متصل لكن الخادم لا يستجيب | وضع محدود + طابور محلي |
| `offline` | لا شبكة إطلاقًا | وضع محدود + طابور محلي |

القيود عند فقد الخادم (تُفحص على الجهاز **وتُعاد** على الخادم عند المزامنة):
جهاز معتمد مسبقًا · نقدي فقط · سقف مبلغ للجهاز · مدة تشغيل محددة ·
**ممنوع**: الآجل، المرتجعات، السيريال، تعديل السعر، صرف النقاط، تغيير الصلاحيات.

عند المزامنة: **لا يُغيَّر مبلغ حُصِّل من عميل بصمت**. أي تعارض يُحفظ للمدير مع المبلغ،
ويقرر هو الاعتماد أو الرفض، والقرار يُسجَّل في التدقيق.

**تخزين المتصفح ليس نسخة احتياطية** — والواجهة تقول ذلك وتوفّر تصدير العمليات المعلقة.

### 3.11 التقارير — تعريف واحد

- `BusinessCalendar` يعرّف "اليوم" مرة واحدة (بتوقيت المحل، مع بداية يوم عمل قابلة للضبط).
- كل تقرير يُرجع `definition` تشرح ما يشمله وما يستبعده.
- كل رقم قابل للفتح على مستنداته (`GET /reports/drill-down`).
- **الإيراد ليس ربحًا**، و**شراء البضاعة ليس مصروفًا**: المشتريات تنتقل للمخزون
  ولا تصل لخط الربح إلا كتكلفة مبيعات.

## 4. لماذا PostgreSQL تحديدًا

النظام يعتمد على قدرات لا يوفّرها SQLite:

- `SELECT ... FOR UPDATE` لأقفال الصفوف
- `INSERT ... ON CONFLICT` للحجز الذري
- فهارس فريدة **جزئية** (`WHERE status IN (...)`) لمنع وردية مزدوجة
- `numeric` بدقة حقيقية
- `pg_trgm` للبحث العربي والإنجليزي
- محفّزات (Triggers) لجعل سجل التدقيق غير قابل للتعديل

**الاختبارات تعمل على PostgreSQL حقيقي**، لا على قاعدة ذاكرة.

## 5. ما هو خارج نطاق هذا الإصدار — بوضوح

- **الصيدليات والأنشطة المنظمة**: تحتاج وحدات مستقلة (وصفات، أصناف مقيدة، تراخيص).
  إضافة منتجات لا تجعل النظام صالحًا لها.
- **الامتثال لمنظومة الفواتير الإلكترونية**: النظام يحسب الضريبة ويفصلها عن الإيراد،
  لكنه **لا يدّعي** الامتثال أو الربط. ذلك يحتاج تكاملًا منفصلًا ومختبرًا.
- **تكامل مزود دفع**: المدفوعات غير النقدية **تسجيل يدوي** لعملية تمت على جهاز خارجي
  (`capture_mode = manual`). البنية جاهزة لإضافة مزود (حالات، مراجع، تسوية) لكنه غير منفَّذ.
- **الطباعة الصامتة والأجهزة الخاصة**: تحتاج وسيطًا محليًا (انظر `docs/HARDWARE.md`).

راجع `docs/STATUS.md` لحالة كل وحدة بالتفصيل.
